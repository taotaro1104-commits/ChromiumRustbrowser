決定(2026-10-26): Chromium の自前ビルドは行わず、**CEF のビルド済み配布物の上で製品化する**(docs/P1-plan.md の選択肢 B)。
`WebContentsHost` で差し替えられる設計は維持するので、将来ビルド環境が用意できれば `crates/chromium-ffi` から Content API へ移れる。

## メモリ予算の再設定
**実測で確定**(2026-10-26、release ビルド、`bench/memory/run-cef-bench.ps1` による自動計測。空きメモリ 5GB 超)。
予算 = 3 回の起動の最大値 + 約 15% の余裕を丸めた値。判定は Private メモリの全プロセス合計の中央値(1 起動あたり 3 サンプル)。

| シナリオ(自動計測の状態) | 設計書(Content API 目標) | 実測(CEF, release) | 予算 |
|---|---|---|---|
| 起動直後(スタートページ 1 枚) | 150MB | 218〜234MB | **270MB** |
| ページ 1 枚(`example.com` だけ。スタートページ無し) | 250MB | 138〜143MB | **170MB** |
| タブ 20 枚(別サイトの実サイト 19 枚 + 既定) | 600MB | 1,046〜1,143MB | **1,350MB** |
| Rust 側 | 20MB | 約 7MB | **20MB**(据え置き) |

- 前回比の失敗ライン: Rust 側は +5%、ブラウザ全体は **+15%**。同じビルドを 3 回測ると、起動 ±7%、20 タブ +9% の差が出たため
  (5% だと同じビルドで失敗した)。前回値は `bench/memory/baseline.txt`(2 回の平均)。
- 手動で「タブを開いてアドレス欄に入力」して測った値(ページ 1 枚 266MB、20 タブ 1,592MB)より小さいのは、起動時に URL を
  直接開く(スタートページと、遷移前のレンダラーが残らない)ためで、状態が異なる。予算は自動計測の状態に対するもの。
- 20 タブ(手動)を破棄すると 1,592MB → 396MB(約 75% 減)、プロセスは 39 → 7。レンダラーが順に終了するため約 90 秒かかる。
- 使い方(`apps/browser/run.ps1 -Release` で一度ビルド・配置してから):
  ```
  powershell -NoProfile -ExecutionPolicy Bypass -File bench/memory/run-cef-bench.ps1 [-Scenarios startup,tabs_20] [-WriteBaseline] [-Sites real|local]
  ```
  シナリオごとに空のプロファイルで起動 → 落ち着くまで待つ → `memory-bench --attach` → 終了、を行う。空きメモリが 4GB 未満なら実行しない。
  終了コードは、通過 0、予算超過/前回比超過 1、準備・計測の失敗 2。`-Sites local` は 127.0.0.N のローカルページで、ネットワークに依らない。
- 起動時の URL は `--url=URL` と `--urls-file=PATH`(1 行 1 URL、最大 50 件)で渡せる。

### 確認バーとパスワード管理(実装済み)
- **確認バー**(`infobar.rs`): ツールバーの下に、メッセージとボタンを出す。質問は一度に 1 つで、出したタブを見ている間だけ表示し、
  5 分で捨てる。ダウンロード・権限など他の確認にも使える。
- **保存**: ページの読込後に `submit` を捕捉する JS を入れ(キー入力は記録しない)、ユーザー名とパスワードを受け取ったら
  「保存 / 今回はしない / このサイトでは保存しない」を尋ねる。パスワードが変わっていれば「更新」を尋ねる。同じ内容なら尋ねない。
- **保存先**: パスワード本体は **Windows の資格情報マネージャー**(`keyring`)。資格情報の名前はサイトやユーザー名を含まないハッシュ。
  DB(`profile.db`)にあるのは「どのサイトにどのユーザー名があるか」の索引だけで、パスワードは入らない(実機で確認)。
- **自動入力**: 保存済みのログインがあるサイトでパスワード欄を見つけたら、「「alice」で入力 / 閉じる」を尋ね、**承認したときだけ**
  最上位フレームの欄へ入れる。質問の後に別サイトへ移っていたら入れない。
- **範囲**: オリジン(スキーム+ホスト+ポート)単位。https のみで、http は開発用のループバック(localhost / 127.0.0.1 / ::1)だけ。
  別ポート・サブドメイン・http は別サイトで、保存済みの情報を渡さない。
- **管理画面**(🔑 ボタン): サイトとユーザー名の一覧と削除。**パスワードは表示しない**。削除すると DB の索引と資格情報の両方が消える。
- **既知の制限**: 受け取ったパスワードの `Zeroizing` による消去は、このクレートが持つ範囲に限る(CEF から文字列を受け取る際の
  複製は消せない)。ページの JS が `console.debug` を差し替えれば、そのページ自身は入力されたパスワードを読める(元々そのページに
  入力した値)。`fetch` だけで送るログイン(`submit` を使わない)は捕捉できない。マスターパスワード/生体認証による再確認は無い
  (OS のサインインに依存)。パスワードの生成・インポート/エクスポートは未実装。

### 残りの未着手
- **アップデータ**: 配布サーバ(署名付きのマニフェストとバイナリ)と、更新用の鍵の管理が前提。サーバ側の用意が決まってから設計する。
  CEF 自体の更新(Chromium のセキュリティ修正の追従)も含むため、公開前の必須項目。
- **クラッシュレポート**: 送信先(サーバ)が前提。CEF は Crashpad を内蔵しており、`crash_reporting` の設定とアップロード先 URL を
  決めれば有効化できる。送信前のユーザー同意の UI も要る。
